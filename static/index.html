Multi-Tenant Architecture

🔑 How Multi-Tenancy Works

This system uses shared database, shared schema multi-tenancy. Every table has an org_id column that acts as a tenant discriminator. When a user logs in, their JWT token contains their org_id, and every API query automatically filters by that org_id. Company A never sees Company B's data.

📐 Database Tables

organizations

Root tenant table. Fields: id, name, slug (unique), plan (enum), industry, created_at

employees

Users and staff. Fields: id, org_id (FK), name, email, password_hash, phone, department, role, position, salary, status, join_date, created_at. UNIQUE(org_id, email)

attendance

Daily attendance records. Fields: id, org_id (FK), employee_id (FK), date, status, check_in, check_out, created_at

leave_requests

Leave requests with approval workflow. Fields: id, org_id (FK), employee_id (FK), leave_type, start_date, end_date, reason, status, created_at

🛡️ Security Model

JWT Tokens contain employee_id, org_id, email, and role. The get_current_user dependency validates the token and verifies the employee exists with matching employee_id AND org_id. The TenantMiddleware sets request.state.org_id before any route handler runs. Admin operations (create/edit/delete employees, approve leaves) require roles: manager, director, vp, or cxo.
